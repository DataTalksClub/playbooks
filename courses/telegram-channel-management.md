## Compare drafts with historical and already posted messages

Use historical candidates for structure and tone. Use the **complete** supplied HTML exports, the latest channel posts, and the delivery ledger to decide whether an action would duplicate a post. The length-filtered extraction omits short operational reminders and cannot establish their absence. Human authorship remains unverified; the user approved treating longer course announcements as candidates.

1. Choose the course, numeric chat ID, cohort slug and entity (such as `hw03`, `midterm` or `capstone1`). Record the message kind: module announcement, homework reminder, submission reminder, review-open notice, peer-review reminder, or navigation. An announcement and a reminder for the same homework are distinct actions.
2. Check exact duplicates by normalizing Unicode, whitespace and case, while preserving meaningful numbers, deadlines and URLs. Store a SHA-256 of the approved final text. An exact match already delivered to that channel/cohort is skipped. Keep raw text too so formatting changes can be reviewed.
3. Compare the tuple `(chat_id, cohort_slug, entity, message_kind)` with posts and queued jobs. The same entity/kind already posted or queued requires review even when phrasing differs. A date correction usually means edit/correction of an identified post, rather than a second release announcement. Editing historical posts by other authors may be unavailable to the bot; check permissions and agree the correction action.
4. Compare UTC deadlines, project/review state, material and submission link destinations, cohort year, dataset, tool guidance, and certificate claims. Treat URLs differing only by cosmetic tracking parameters as equivalent for duplicate review; never collapse distinct homework/project paths or cohorts. Repeated curriculum text in another year is a reuse candidate, not a duplicate delivery.
5. Report similarities as review flags, with the matched message IDs/URLs and factual differences. Never use a text-similarity threshold alone to send or delete a post. Record a decision: skip exact duplicate, update existing draft, propose edit/correction, prepare distinct reminder, or hold for missing facts.
6. Immediately before execution, refresh live facts and channel history, recheck queued jobs and approval, then use the exact approved file hash. If a deadline or file changed after approval, update the review table before executing that changed content. Store returned Telegram message ID and actual send time only after confirmed success. A timeout is uncertain delivery; investigate rather than blindly retry.

The Bot API does not provide a retrospective channel-history listing. Public channel previews, the supplied exports, or an authorized Telegram user session are needed for older posts. Incoming bot updates and returned `message_id` values can maintain history going forward; adding the bot today does not reconstruct old posts.
